# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer is responsive | `repo_facts.raw_markdown` — the "maintainer first-response sample" line and its listed issues | Fail only if every sampled issue shows "no maintainer comment in thread" AND at least one was opened more than 7 days before the bundle's capture date (enough time to have gotten a response). If every sampled issue was opened within 7 days of capture, there hasn't been enough time to judge fairly — pass by default. Unclear if `raw_markdown` has no "maintainer first-response sample" line at all. | required |
| Repo is in use | `repo_facts.raw_markdown` — the `archived:` flag, `last push to any branch:` date, and `latest release:` date, measured against the bundle's `captured` date | Fail immediately if `archived: yes`. Otherwise pass if `last push to any branch` is within 90 days of the capture date, OR `latest release` is within 180 days of the capture date. Unclear if archived, last-push, and release date are all missing. | required |
| Scope fits a newcomer | `issue.labels`, `issue.body_markdown`, `repo_facts.linked_prs`, and the comment thread | Fail if ANY of: labels contain `needs-design`, `architecture`, `epic`, or `tracking`; the body describes 3+ distinct items that each require new logic, new design decisions, or substantial new content as separate concerns — not counting brief pointer/reference updates to other files, items explicitly framed as optional/additional/suggested, or several listed potential causes of one symptom (diagnostic hypotheses, not separate deliverables); a list of several small, same-shaped changes following one repeated pattern counts as one bounded task, not 3+ distinct items; the comment thread shows unresolved design disagreement with no maintainer decision recorded; the issue has been open for multiple years and shows 2 or more closed, unmerged linked PRs in its history (repeated abandoned attempts signal real hidden difficulty). Pass otherwise. Unclear only if the body is empty or contains just a title, with no real description of the problem or request. | required |
| Nobody's already on it | `repo_facts.assignees`, `repo_facts.linked_prs`, and the comment thread (thread takes precedence over structured fields when they conflict) | Fail if ANY of: `assignees` is non-empty; `linked_prs` contains any entry marked (open) — this is an unconditional fail unless the comment thread explicitly confirms that specific PR was abandoned or superseded, so don't let unrelated claim chatter in the thread override a structured open-PR entry; the comment thread contains claim language ("I'll take this", "working on this", "can I work on this") with no clear abandonment signal (no follow-up after 60+ days, or the commenter says they've dropped it). Pass otherwise — a closed/unmerged linked PR or an old, unfollowed claim comment does not fail this check. Unclear if a claim comment's status is ambiguous. | required |
| Contribution policy allows this workflow | `repo_facts.raw_markdown` — the "contribution policy" line | Fail only if the policy states an outright ban on AI-assisted or AI-generated contributions (e.g., "we do not accept AI-generated code"). Pass if the policy sets conditions (disclosure, human review, testing, understanding requirements) or says nothing about AI at all — silence passes. | required |
| Issue has a clear description | `issue.body_markdown` | Pass if the body contains at least one of: reproduction steps, a specific file or function named, or an explicit expected vs actual behavior description. Fail if the body is only a title with no elaboration. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails or is unclear (unclear counts as fail). Preferred checks never change the verdict — they are used only to rank accepted issues against each other when choosing which one to work on.
